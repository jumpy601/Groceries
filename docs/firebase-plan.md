# 第二階段：Firebase 設計（草案，待使用者確認）

> 狀態：**需求已確定、做法待確認**。動工前要先和使用者確認第 4 節的問題。

## 1. 已確定的需求

### 家人共用
- 家裡兩個人共用同一份資料，即時同步。
- LINE 機器人：在群組打「待買」，機器人回覆待買清單。
- LINE 每週推送一次摘要。

### 個人島串接（2026-10-31 使用者指定）
1. **島專用帳號**（電子郵件／密碼）。安全規則只允許它：
   - **讀取庫存**
   - **寫入「本週菜單食材」這一區**
   - 不能修改、也不能刪除其他資料
2. **「本週菜單食材」在待買清單裡獨立一區**（「本週菜單」），和庫存品分開顯示，兩個人都能按「已買到」。
3. **小倉庫的公開網頁不放任何島的金鑰**。島的帳號密碼只存在島的排程設定裡（例如 GitHub Secrets）。

## 2. 資料結構草案（Firestore）

```
households/{hid}                 家庭本體：名稱、settings、members、islandUid
  ├ categories/{catId}           分類
  ├ items/{itemId}               物品（含 batches 效期批次）
  ├ logs/{logId}                 變動紀錄（一筆一份文件，避免單一文件超過 1MB）
  ├ checks/{id}                  緊急備品檢查紀錄
  ├ menuWeeks/{week}_{rev}       島寫入的本週菜單（只能新增，不能修改）
  └ menuStatus/{week}_{key}      家人按「已買到」的狀態
```

- 每個物品各自一份文件，不把整包資料塞進同一個文件。這樣安全規則才能針對不同的區塊分別設定權限。
- `members`（家人的 uid）和 `islandUid` 只有家庭建立者能修改。島的帳號不能改到它們。

### 本週菜單（草案 B：只能新增）
- 島每次產生菜單，就**新增**一份 `menuWeeks/{week}_{rev}`：
  - 欄位：`week`（例如 `2026-W45`）、`rev`、`createdBy`、`items[]`
  - `items` 每一項：`key`（島給的固定代碼）、`name`、`amount`（文字，例如「300g」）、`dish`（給哪道菜）、`note`
- 小倉庫顯示「這週最新的一版」。
- 「已買到」記在另一個地方 `menuStatus/{week}_{key}`：
  - 欄位：`bought`、`by`、`at`
  - 只有家人能寫入
  - 因為存在不同的地方，島重新產生菜單時不會把已買到的狀態洗掉

## 3. 安全規則重點（草案）

| 區塊 | 家人 | 島帳號 | 其他登入者 |
|---|---|---|---|
| households 本體 | 讀；建立者可改 members／islandUid | ✗ | ✗ |
| categories、items | 讀寫 | **只能讀** | ✗ |
| logs、checks | 讀寫 | ✗（待確認） | ✗ |
| menuWeeks | 讀、可刪舊的 | **只能新增**，並檢查欄位格式與 `createdBy` | ✗ |
| menuStatus | 讀寫 | 讀 | ✗ |

### 金鑰
- 網頁裡會有 Firebase 的設定值（apiKey、projectId）。這是 Firebase 刻意設計成可以公開的，**不是島的金鑰**。真正的保護靠的是安全規則。
- 島的帳號密碼只放在島的排程設定裡。

### 自行註冊
- 任何人只要拿到公開的 apiKey，都能自己註冊一個帳號。
- 規則只認 `members` 和 `islandUid` 裡的 uid，所以陌生人註冊了也讀不到任何資料。
- 如果 Firebase 主控台可以關閉「自行註冊」，就一併關掉。
